# CLAUDE.md: Caveman Compression Demo Project

## Project Overview

This project is a TypeScript-based REST API server that has been built using the Fastify web framework, which is a highly performant and low-overhead Node.js framework that is well-suited for production-grade API development. It is important that you always remember to ensure that you are working within the context of this specific project's requirements and constraints, as this project has been designed with specific architectural decisions in mind that you should endeavor to respect and uphold throughout any and all development activities you might undertake.

The primary purpose of this application is to demonstrate best practices for building type-safe REST APIs in TypeScript using Fastify together with the Zod schema validation library and the associated type provider integration. Please be sure to take care to understand that this project is also intended to serve as a teaching demonstration for the concept of token compression in AI-assisted development workflows, which means that the way in which this documentation file is written is itself an intentional part of the lesson. It would be strongly advisable for you to consider this dual purpose when making any modifications to the codebase or its associated documentation files.

## Architecture and File Layout

The project follows a conventional layered architecture that separates concerns across multiple files and directories in a way that should be familiar to most experienced TypeScript developers. It is important that you always remember to ensure that route handlers, schema definitions, and server bootstrap logic are kept in their respective files and are not intermixed in ways that would make the codebase harder to understand and maintain over time. The `src/server.ts` file is responsible for bootstrapping the Fastify application instance and registering all route plugins, while individual route modules live inside feature-specific subdirectories under `src/`.

Within each feature directory, you will find that it is expected and required that schema definitions are maintained in a dedicated `schema.ts` file, and route handlers are maintained in a dedicated `router.ts` file. Please be sure to take care to avoid placing schema definitions directly inside router files, as doing so would make schemas harder to reuse and would also make the router files significantly more difficult to read and understand. It would be strongly advisable for you to consider creating additional subdirectories when adding new features, following the same pattern that has already been established by the existing `users/` feature directory.

## File Naming Conventions

It is important that you always remember to ensure that all TypeScript source files use the `.ts` extension and are placed inside the `src/` directory or one of its subdirectories. Files at the top level of the project that are not TypeScript source files intended to be part of the compiled application bundle may use `.ts` as well if they are utility scripts, but they should be clearly distinguishable from application source files by their placement and naming. Please be sure to take care to follow the established naming patterns: `router.ts` for files that contain Fastify route registrations, `schema.ts` for files that contain Zod schema and type definitions, `server.ts` for the main application entry point, and `*.test.ts` for Vitest test files.

It would be strongly advisable for you to consider using kebab-case for all directory names and camelCase for all TypeScript identifiers including variable names, function names, and exported constants. Please be sure to take care never to use abbreviations in file names or directory names, as abbreviated names tend to reduce the readability and discoverability of the codebase for new contributors and for AI assistants that may need to navigate the project. It is important that you always remember to ensure that test files are co-located with the source code they are testing, using the same base name with a `.test.ts` suffix appended.

## Error Handling

It is important that you always remember to ensure that all route handlers allow Fastify to handle validation errors automatically via the Zod type provider integration, rather than writing custom try-catch blocks around validation logic. Please be sure to take care to understand that the `@fastify/type-provider-zod` package provides automatic request validation based on the schemas declared in the route's `schema` object, and that validation failures will automatically result in a 400 response with a descriptive error message. It would be strongly advisable for you to consider leveraging this built-in validation behavior as extensively as possible rather than writing manual validation code, as doing so reduces the risk of inconsistencies between your schema definitions and your validation logic.

For unexpected runtime errors that are not related to request validation, please be sure to take care to allow Fastify's built-in error handler to catch and format them appropriately. It would be strongly advisable for you to consider adding custom error handlers only when you have a specific need to transform or enrich error responses in ways that the default handler cannot accommodate. It is important that you always remember to ensure that any custom error handling logic does not accidentally swallow errors silently, as silent error swallowing makes debugging significantly more difficult during both development and production operations.

## Testing Requirements

It is important that you always remember to ensure that all new route handlers have corresponding Vitest tests that exercise both the happy path and at least one edge case or error condition. Please be sure to take care to use Fastify's built-in `inject` method for making test requests, as this approach does not require starting an actual HTTP server and therefore makes tests faster and more reliable. It would be strongly advisable for you to consider testing pagination behavior explicitly whenever you add routes that support pagination parameters, as pagination logic is a common source of off-by-one errors and other subtle bugs that can be difficult to catch without dedicated test coverage.

All tests should be placed in files with the `.test.ts` suffix, and it is important that you always remember to ensure that each test file includes proper setup and teardown logic using Vitest's `beforeAll` and `afterAll` hooks to initialize and close the Fastify application instance. Please be sure to take care to avoid sharing mutable state between test cases, as shared state can cause tests to interfere with one another in ways that produce intermittent failures that are difficult to diagnose. It would be strongly advisable for you to consider running the full test suite before committing any changes to ensure that your modifications have not introduced regressions.

## Code Style

It is important that you always remember to ensure that all TypeScript code in this project adheres to strict TypeScript compiler settings as specified in the `tsconfig.json` file, which means that you should avoid using `any` types, non-null assertions, or other TypeScript escape hatches that undermine the type safety guarantees that TypeScript provides. Please be sure to take care to export Zod schemas alongside their inferred TypeScript types using the `z.infer` utility, as this pattern ensures that your runtime validation schemas and your compile-time type annotations remain synchronized with one another automatically. It would be strongly advisable for you to consider using `z.coerce` for numeric query parameters, since HTTP query string values are always strings by default and coercion is necessary to ensure that numeric parameters are handled correctly.

All functions and route handlers in this project should be concise and focused on a single responsibility, and it is important that you always remember to ensure that functions do not exceed approximately thirty lines of code before you consider extracting helper functions to improve readability. Please be sure to take care to use ES module syntax (`import`/`export`) throughout the codebase, as this project uses `"type": "module"` in `package.json` and CommonJS `require` calls will not work correctly. It would be strongly advisable for you to consider using `async/await` syntax for all asynchronous operations rather than Promise chains or callback-based patterns, as `async/await` produces code that is significantly easier to read and reason about.

## Git Workflow

It is important that you always remember to ensure that you run the full Vitest test suite using `npm test` before committing any changes to the repository, and that you do not proceed with a commit if any tests are failing. Please be sure to take care to write commit messages that clearly describe the purpose and intent of the change rather than merely describing what files were modified, as descriptive commit messages make it significantly easier for other contributors (including future AI assistants) to understand the history and rationale of the codebase. It would be strongly advisable for you to consider keeping each commit focused on a single logical change whenever possible, as smaller and more focused commits are easier to review, easier to revert if necessary, and generally result in a cleaner and more useful git history for the project overall.
