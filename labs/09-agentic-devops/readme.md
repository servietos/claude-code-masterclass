Every lab ships in two editions that teach the same steps. The **local container** edition runs the box as a container on Docker on your own machine. The **Azure lab VM** edition runs the same lab on an Ubuntu VM your instructor provides, with Docker Engine, Node.js, Google Chrome and Claude Code preinstalled, so your own machine needs only an SSH client. Pick one edition and stay with it: Labs 02 to 04 reuse the box Lab 01 built.

The instructor creates the lab VMs with [create-lab-vm.azcli](create-lab-vm.azcli). It asks for the number of VMs, installs the tools on each one through [cloud-init.yaml](cloud-init.yaml), and writes every VM's public IP, user and password to `azure-linux.md` for handing out.

**Core** is the one lab that teaches this module's central capability; run it if you run nothing else. **Optional** labs go deeper or cover a second build pipeline. **Level** rates the lab itself: Beginner needs no prior Claude Code experience, Intermediate assumes you have configured a harness before, Advanced assumes you are comfortable with hooks, subagents, or headless scripting.

Core path: 1h 30m. All labs: 4h 45m.

Every lab needs a working Docker installation, which is why no figure includes a Docker install. Lab 04 also runs `npx` tools on your machine, so it needs Node.js and Chrome there.

Lab 01 is Core because it is the module itself: a containerized app on a plain Ubuntu host reached over SSH, which is the deployment every demo in this module builds toward. It is rated Advanced because it hardens a live host, writes a scoped sub-agent, and requires you to distinguish an agent's claim from the host's answer. Labs 02 and 03 are the same host reached through a simpler pipeline: the edge and the certificate are dropped so each lab isolates one delivery path, Lab 02 the containerized app build, Lab 03 a static site whose entire toolchain lives inside the build.

Every path here stays account-light. The local container editions need only Docker on your own machine, because the deployment target is a throwaway Ubuntu container running `sshd` that stands in for a VM. No lab in this module needs a cloud subscription, a credit card, or a provider console.

## Prerequisites

- The Azure lab VM editions need the **access data for your lab VM** (public IP, user and password) and an `ssh` client on your own machine; Docker Engine, Node.js, Google Chrome and Claude Code are preinstalled on the VM.
- The local container editions need **Docker Desktop or Docker Engine** running, with `docker compose` v2 available, plus a **bash shell** (git-bash or WSL on Windows) for its `ssh` and pipe syntax. It needs no GitHub account and no local Node or Hugo install, because every build runs inside a container. On Windows, [Install WSL and Docker Desktop](install-docker-desktop.md) covers both in one pass.
- Lab 01 needs **Claude Code 2.x**, because Step 9 writes a sub-agent definition.
- Labs 02 and 03 build on Lab 01: they need its box running with the `deploy` user, Docker, and the `vfs` storage driver in place.
- Lab 04 builds on Lab 01 through Step 8: it needs the box and the Caddy edge running, the `react-devops/deploy/` folder still in place for its key and CA certificate, **Node.js 20 or newer**, **Google Chrome**, and the global `agentic-seo` skill.

Lab 01 and Lab 02 share the same starter at `react-devops/`. Work there and keep it pristine: no `node_modules`, no build output, no test reports committed back. Build your own result from the guide first and treat a solution folder as a check.

`publish-blog/` is a design reference only. It is a real deployed Hugo site kept here so you can read its configuration and build. Never use it as a working directory for any lab.

The starter's `.gitignore` already covers `playwright-report/`, `test-results/`, `blob-report/` and `playwright/.cache/`, so running the end-to-end suite leaves `git status` clean. `package-lock.json` is committed on purpose: the Dockerfile's `npm ci` needs it. No lab in this module requires the end-to-end suite.
