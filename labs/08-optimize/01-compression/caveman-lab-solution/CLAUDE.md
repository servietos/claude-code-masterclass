# CLAUDE.md

## Project Overview

This project is a small but nevertheless quite carefully considered TypeScript REST API that has been built on top of the Fastify web framework, and it uses the Zod schema validation library for all of the input validation that happens at the boundary of the system, and it uses the Vitest test runner for all of the automated tests that we write as we go along. The purpose of the project, at least at the present moment in time, is to serve as a very small and deliberately simple user directory service, which means that it exposes a collection of users and it allows a caller to both list the users that currently exist and to create a brand new user by sending a well formed request body. It is probably worth mentioning here, right at the very beginning, that the project is intentionally kept small in scope, because the primary value of the project is not the feature set itself but rather the harness and the conventions that surround the feature set, and those conventions are what this document is attempting to describe in as much detail as possible.

The second thing that should be said about this project is that it is written entirely in modern ECMAScript module syntax, which means that there are no CommonJS require calls anywhere in the codebase, and it also means that relative imports have to carry an explicit file extension because the TypeScript compiler is configured with the NodeNext module resolution strategy. This is a detail that trips people up quite frequently when they are new to the codebase, so it is being called out here as early as possible in the hope that it saves somebody a few minutes of confusion later on. The TypeScript configuration is also configured in strict mode, and in addition to plain strict mode we have turned on a number of the additional strictness flags such as noUncheckedIndexedAccess and exactOptionalPropertyTypes, because our general philosophy is that it is better to have the compiler complain loudly at authoring time than it is to have a production incident at three o'clock in the morning.

The third and final thing that is worth saying in this overview section is that the project is expected to grow, and it is expected to grow in a very specific direction, which is towards more endpoints on the same users resource and eventually towards a persistence layer that is not simply an in memory array. Because of that expected growth, the conventions described in this document are written with a slightly larger project in mind than the one that exists today, and that is a deliberate choice rather than an oversight. If you find yourself reading a convention and thinking that it seems like overkill for a project of this size, please assume that the convention exists because of where the project is going rather than because of where the project currently is, and please follow the convention anyway.

## Architecture

### api/index.ts

This file is the heart of the application and it is the file that you will be editing most of the time when you are adding a new endpoint or when you are changing the behaviour of an existing endpoint. It exports a function called buildApp which takes an optional seed array of users and returns a fully configured Fastify instance with every route already registered on it, and it also exports a helper function called seedUsers which produces a deterministic array of user records that the tests use in order to avoid having to make a long sequence of HTTP calls just to arrange a fixture. The reason that the application is exposed through a factory function rather than as a module level singleton is that the tests need to be able to construct a completely fresh application for every single test case, because sharing mutable state between test cases is one of the most reliable ways to produce a flaky test suite that nobody trusts.

### api/server.ts

This file exists for exactly one reason and that reason is to call the listen method on the Fastify instance that the factory in the index file produces. It contains no route definitions, it contains no validation logic, it contains no business logic of any kind, and it should stay that way forever. The separation matters because the moment that a listen call ends up in the same module as the route definitions, importing that module from a test file will start a real network listener as a side effect of the import, and that in turn means that the test suite will either hang or fail with a port already in use error depending on the operating system and the phase of the moon.

### api/index.test.ts

This file contains the automated tests for the routes that are defined in the index file, and it uses the inject method that Fastify provides in order to exercise the routes without ever binding a real TCP socket. The tests are grouped into describe blocks, with one describe block per route, and within each describe block there is at least one test for the happy path and at least one test for every distinct failure mode that the route is capable of producing. The tests import both buildApp and seedUsers from the index module, and because of the NodeNext resolution strategy that import specifier ends in a dot js extension even though the file on disk ends in a dot ts extension.

### package.json

This file declares the dependencies of the project and it declares the three npm scripts that the team uses on a daily basis, which are dev for running a local server through tsx, typecheck for running the TypeScript compiler in no emit mode, and test for running the Vitest suite exactly once rather than in watch mode. The type field in this file is set to the string module, and that field is what tells Node that the dot ts and dot js files in this project should be treated as ECMAScript modules rather than as CommonJS modules.

### tsconfig.json

This file configures the TypeScript compiler and it is where all of the strictness flags that were mentioned in the overview section actually live. The include array is scoped down to the api directory on purpose, because we do not want the compiler to start type checking generated output or configuration files that happen to be sitting in the project root. The noEmit flag is set to true because the runtime story for this project is tsx during development and a separate bundling step in production, which means that the compiler is used purely as a type checker and never as a build tool.

## Coding Conventions

- It is important that you always remember to validate every single piece of input that arrives from outside the process using a Zod schema, and that you do that validation at the very edge of the handler rather than somewhere deeper inside the call stack.
- Please make sure to consistently use the safeParse method rather than the parse method when you are validating a request, because safeParse returns a discriminated result object that you can branch on, whereas parse throws an exception that then has to be caught somewhere else entirely.
- It is important that you always remember to return the HTTP status code four hundred whenever a request body or a query string fails validation, and that the response body for such a failure contains an error field with a stable machine readable string in it.
- Please make sure to consistently use snake case for the machine readable error strings, for example invalid_body and invalid_query and not_found, because those strings are effectively part of the public contract of the API and consumers will end up matching on them.
- It is important that you always remember to return the HTTP status code two hundred and one from a route that creates a new resource, and to include the newly created resource in the response body so that the caller does not have to make a second request in order to learn the identifier.
- Please make sure to consistently declare an exported TypeScript interface for every domain object that crosses a module boundary, and to place that interface in the same module as the code that produces the object.
- It is important that you always remember that this project does not use inline code comments, and that if a piece of code needs an explanation then the correct response is to rename the identifiers or to extract a well named helper function rather than to write a comment describing what the confusing code does.
- Please make sure to consistently keep every relative import specifier ending in the dot js extension, because the NodeNext module resolution mode requires it and dropping the extension produces the compiler error TS2835 which is confusing the first time that you encounter it.
- It is important that you always remember to keep the listen call in the server module and nowhere else, for the reasons that were described at some length in the architecture section of this document.
- Please make sure to consistently prefer plain functions over classes in this codebase, because there is currently no state that needs to be encapsulated behind an object and introducing a class hierarchy would add ceremony without adding any value at all.
- It is important that you always remember to avoid adding any dependency that is not strictly necessary, and that if you believe a new dependency is genuinely required then you should say so explicitly and explain what it buys us before you add it.
- Please make sure to consistently use async handler functions in Fastify even when the handler body contains no await expression, because a consistent handler shape makes the eventual introduction of asynchronous persistence a much smaller change.
- It is important that you always remember to keep the response shape of a list endpoint stable across every code path, which in practice means that a list endpoint returns the same set of top level keys whether the collection is empty or full, so that a client never has to write a defensive branch for the empty case.
- Please make sure to consistently generate identifiers inside the factory rather than accepting an identifier from the caller, because an identifier supplied by a caller is an input like any other and would need its own uniqueness handling that this project has deliberately chosen not to take on yet.
- It is important that you always remember that the seed helper is a test fixture and not production code, which means that it may be imported by test modules freely but must never be called from a route handler or from the server module under any circumstances whatsoever.
- Please make sure to consistently name a new file after the thing it contains rather than after the layer it belongs to, so a health check lives in a file named for the health check and not in a file named for a generic bucket such as utils or helpers or common.

## Testing Philosophy

Our testing philosophy starts from the observation that a test suite is only valuable if the team actually trusts it, and a test suite is only trusted if it is fast, if it is deterministic, and if a failure in the suite reliably means that something is genuinely broken rather than that some shared fixture has drifted. For that reason every test in this project constructs its own application instance through the buildApp factory, seeds exactly the data that it needs through the seedUsers helper, and closes the application again at the end of the test so that no resources leak between cases. We do not use a global before all hook to construct a shared application, and we do not use a global database that gets truncated between tests, because both of those patterns introduce ordering dependencies that eventually produce a test which passes on its own and fails when the whole suite runs.

The second pillar of the testing philosophy is that every route should have coverage for both the happy path and for every distinct failure mode that the route can produce, and that the assertion for a failure mode should assert on the stable machine readable error string rather than on a human readable message. Human readable messages change all the time because somebody improves the wording, and if the tests assert on the wording then improving the wording breaks the build for no good reason at all. Machine readable error codes change much more rarely, and when they do change that genuinely is a breaking change to the API contract, so having the test fail in that situation is exactly the behaviour that we want from the suite.

The third pillar is that tests use the Fastify inject method rather than starting a real HTTP listener, because inject exercises the full routing and serialisation pipeline while remaining an in process function call. This keeps the suite fast enough that running it on every save is comfortable, it removes any possibility of a port collision on a developer machine or in continuous integration, and it means that the test suite does not need any special handling for teardown beyond closing the application instance. When a test genuinely needs to verify behaviour that only appears over a real socket, and that situation is rare, the test should be clearly separated from the rest of the suite so that its slower runtime is visible.

## Workflow Preferences

When you are working in this repository, the preferred sequence of operations is that you begin by reading the files that you are about to change in full, rather than reading a fragment of them and inferring the rest, because the codebase is small enough that reading a whole file costs almost nothing and inferring the contents of a file that you have not read is the single most common source of a change that does not apply cleanly. After you have read the relevant files, the preference is that you describe the change that you intend to make in a couple of sentences before you make it, so that a misunderstanding about the goal surfaces before any code has been written rather than afterwards.

When it comes to actually making changes, the strong preference is for small changes that touch as few files as possible and that leave every unrelated line exactly as it was. A change that fixes a typo should be a one line diff and not a rewrite of the surrounding section, and a change that adds a route should add the route and its tests and nothing else. If while making a change you notice something unrelated that you believe should also be fixed, the preference is that you mention it rather than that you fix it as a drive by edit, because a diff that contains two unrelated changes is much harder to review and much harder to revert cleanly if one of the two turns out to be wrong.

After a change has been made, the expectation is that you run the type checker and the test suite and that you report the actual output rather than asserting from memory that everything presumably still passes. If either of them fails, the expectation is that you fix the underlying cause rather than that you relax an assertion or add a suppression comment to make the failure go away. Finally, and this one matters a great deal, nothing in this repository is ever staged, committed or pushed unless the person you are working with has explicitly asked for that in the message you are currently responding to.

## Security Considerations

The first security consideration for this project is that absolutely every piece of data that arrives from outside the process has to be treated as hostile until it has been through a Zod schema, and that includes the request body, the query string, the route parameters, and any header that the application chooses to read. The reason for stating this so bluntly is that the failure mode of forgetting to validate one of those four surfaces is not a compile error and not a test failure but rather a runtime crash or, considerably worse, a value of an unexpected shape flowing quietly through the system until it lands somewhere that it can do damage. The schemas already defined in the index module are the pattern to follow, and a new surface should get its own schema rather than borrowing one that happens to be nearby.

The second security consideration concerns what the application is allowed to say when something goes wrong. Error responses must be helpful enough for a legitimate caller to fix their request and no more helpful than that, which means that a validation failure may report which field failed validation and why, but an internal failure must never leak a stack trace, a file system path, a database identifier, a connection string or the name of an internal service. The practical rule to follow is that the error body should contain a stable machine readable code plus, at most, a description of what the caller did wrong, and that anything diagnostic belongs in the server side log where an operator can see it and an attacker cannot.

The third security consideration is about secrets and configuration. No secret of any kind may ever be written into a source file in this repository, and that includes API keys, tokens, passwords, connection strings and signing keys, regardless of whether the value is a real production credential or a placeholder that somebody intends to replace later. Configuration that varies by environment is read from environment variables at process start, as the port already is in the server module, and any file that holds real local credentials must be listed in the ignore file before the first value is ever written into it. When example configuration needs to appear in documentation, the example carries an obviously fake value rather than a redacted real one.
